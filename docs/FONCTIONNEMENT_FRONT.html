    GSB — Comprendre le front, de A à Z

    Guide d'étude du dossier frontend/ : comment chaque fonctionnalité marche, quel fichier fait quoi, pourquoi le code est écrit comme ça, et comment défendre tes choix à l'oral. Écrit le 11/11/2026, d'après le code de la branche kelian.

    Comment lire ce guide Les sections 1 à 3 donnent les bases (démarrage, React, données). Les sections 4 à 12 détaillent chaque fonctionnalité fichier par fichier. La section 13 déroule des parcours complets pas à pas, la 14 liste les règles métier, la 15 la sécurité et le RGPD, la 16 ce qui change avec le back-end. Les noms entre code sont de vrais fichiers, fonctions ou variables : ouvre-les à côté.
    Ce guide explique chaque fichier et chaque bloc de logique, pas chacune des ~7 000 lignes une par une : les lignes purement visuelles (CSS, décor 3D) sont résumées.

    1. Vue d'ensemble

    Le front est une application web React (une « SPA » : Single Page Application). Le navigateur charge une seule page HTML ; ensuite, React change l'affichage sans recharger la page quand on clique sur un lien. Il n'y a aucun serveur pour l'instant : les données sont des fichiers JavaScript (« mocks ») et le navigateur sert de mini-base de données.

    Arborescence

    frontend/
├─ index.html            la page unique ; contient <div id="root">
├─ public/               fichiers servis tels quels (images produits, vidéos)
└─ src/

   ├─ App.jsx            la table des routes (adresse → page)
   ├─ features/          UN dossier par fonctionnalité (auth, cart, catalogue, …)
   ├─ components/        briques partagées : ui/, icons/, effects/

    La règle d'organisation (FRYDAY.md) Ce qui sert à une seule fonctionnalité vit dans son dossier features/<nom>/ (composant, CSS, hook, service, données). Ce qui sert à plusieurs fonctionnalités va dans components/ ou utils/. Dans chaque fichier, les imports suivent le même ordre : bibliothèques → autres dossiers du projet → même dossier → CSS.

    2. Le démarrage : de index.html à l'écran

    navigateur ouvre localhost:5173 → index.html (contient <div id="root"> et charge /src/main.jsx) → main.jsx : createRoot(#root).render( … ) StrictMode └ BrowserRouter (active les adresses / liens) └ AuthProvider (qui est connecté ?) └ CartProvider (son panier) └ App (quelle page pour cette adresse ?)

    main.jsx

    • StrictMode : en développement seulement, React exécute chaque effet deux fois pour révéler les bugs. C'est pour ça que le code des gélules a un test pills.length > 0 (voir section 6).
    • BrowserRouter doit entourer tout ce qui utilise Link, useNavigate, useLocation.
    • L'ordre des providers compte : CartProvider lit l'utilisateur (useAuth), donc il doit être à l'intérieur de AuthProvider. Si on les inverse, useAuth lève une erreur claire (« doit être utilisé à l'intérieur de <AuthProvider> »).
    • Il importe styles/global.css, qui importe lui-même la police et tokens.css.

    App.jsx : la table des routes

    Une route = une adresse + le composant à afficher. Elles sont imbriquées pour partager des protections :

    <Routes>
  /                    → redirige vers /connexion
  /connexion           → LoginPage
  /mot-de-passe        → ChangePasswordPage        (hors protection, sinon boucle)
  <Route element={<ProtectedRoute><AppLayout/></ProtectedRoute>}>   ← connecté obligatoire + en-tête
      /compte          → AccountPage               (les 3 profils)
      <Route element={<ProtectedRoute roles={[Professionnel]} />}>
          /accueil /catalogue /catalogue/:productId /panier
          /commande /commande/confirmation/:orderId /commandes /commandes/:orderId
      <Route element={<ProtectedRoute roles={[Administrateur]} />}>
          /admin → /admin/commandes, /admin/produits(/nouveau|/:productId),
          /admin/validation, /admin/categories, /admin/comptes
      <Route element={<ProtectedRoute roles={[Fournisseur]} />}>
          /fournisseur → /fournisseur/produits(/nouveau|/:productId)
  *                    → NotFoundPage
    • :productId est un paramètre d'adresse : le composant le lit avec useParams().
    • Une route « de mise en page » (avec element mais sans path) affiche ses enfants à la place de <Outlet />. C'est ainsi que AppLayout met l'en-tête autour de toutes les pages.
    • Une ProtectedRoute sans enfant explicite rend <Outlet /> : elle sert de « portier » pour tout un groupe de pages.

    4. Les données : mocks, services, stockage navigateur

    Comme il n'y a pas de serveur, chaque fonctionnalité a un service qui joue le rôle du serveur. Les composants appellent le service ; plus tard on remplacera le contenu du service par des fetch vers l'API Express, et les composants ne changeront pas.

    mocks/delay.js

    delay(ms = 500) renvoie une promesse qui se résout après 500 ms. Chaque service l'attend (await delay()) pour simuler le temps d'un vrai réseau : on voit donc bien les écrans « Chargement… ».

    utils/useLoader.js : l'état d'un chargement

    Presque toutes les pages chargent des données. Ce hook gère les 3 états (exigés par FRYDAY : chargement / erreur / vide).

    const { status, data, reload } = useLoader(load);
// status : 'loading' | 'error' | 'success'
// data   : le résultat de load() (null tant que ce n'est pas chargé)
// reload : relance le chargement (bouton « Réessayer », ou après une modification)
    1. run() met l'état à loading — sauf s'il y a déjà des données affichées (previous.status === 'success') : au rechargement après une modification, la liste ne clignote pas.
    2. Elle appelle await load() ; succès → {status:'success', data}, échec → {status:'error'} (le détail technique n'est pas montré à l'utilisateur).
    3. Un useEffect lance run au premier affichage et chaque fois que load change. C'est pourquoi load doit être stable : on l'enveloppe dans useCallback.

    components/ui/PageState.jsx

    Le complément d'affichage de useLoader : <PageState status isEmpty emptyText onRetry>…enfants…</PageState>. Chargement → « Chargement… » (aria-busy) ; erreur → message + bouton « Réessayer » (role="alert") ; vide → le texte emptyText ; sinon → les enfants. Toutes les nouvelles pages (commandes, admin, fournisseur) l'utilisent : elles réagissent donc toutes pareil.

    Pourquoi si peu dans le navigateur ? FRYDAY interdit les tokens et données sensibles dans localStorage : tout le monde peut le lire et le modifier dans les outils du navigateur. On n'y met donc ni mot de passe, ni jeton ; le panier ne contient pas de prix (voir section 9) ; et chaque lecture est re-validée (« on ne fait pas confiance au stockage »). Les mots de passe des comptes restent en mémoire seulement.

    Toutes les lectures/écritures de stockage sont entourées de try/catch : en navigation privée stricte le stockage peut être indisponible ; l'appli continue de marcher, sans mémoire d'une page à l'autre.

    Exigences : F03 (connexion), F04/RG04 (mot de passe à changer à la première connexion), F02 (pas d'inscription), F07 (pages protégées), NF02 (contrôle par rôle), NF04 (message d'erreur générique).

    FichierRôle détaillé

    authService.login(email, password) pas à pas

    1. await delay() (simule le réseau).
    2. Cherche l'utilisateur dont l'email (trim().toLowerCase()) correspond.
    3. Si l'utilisateur n'existe pas ou si le mot de passe est faux ou si le compte est désactivé → lève la même erreur : « Email ou mot de passe incorrect. » NF04 On ne révèle jamais si l'adresse existe (sinon un attaquant pourrait deviner quelles adresses sont des comptes).
    4. Sinon : saveSession(user.id) (écrit uniquement le numéro dans sessionStorage) et renvoie toPublicUser(user), la copie sans le champ password (const { password: _p, ...publicUser } = user). Le reste de l'appli ne voit donc jamais un mot de passe.

    restoreSession()

    Appelée une seule fois, au tout premier rendu de AuthProvider : useState(() => authService.restoreSession()). (Passer une fonction à useState = « calcule la valeur initiale une seule fois ».) Elle relit gsb.userId, retrouve l'utilisateur actif et le renvoie ; sinon null. C'est ce qui fait qu'un F5 ne déconnecte pas.

    useLoginForm (la logique du formulaire)

    values {email, password}   errors {email?, password?}   formError   isSubmitting
handleChange   : met à jour la valeur du champ modifié (event.target.name / value)
validate()     : email invalide → message ; mot de passe vide → message
handleSubmit   : preventDefault ; si déjà en cours → return (anti double clic) ;
                 si erreurs → les afficher et s'arrêter ;
                 sinon login() ; succès → navigate(mustChangePassword ? '/mot-de-passe' : homePathFor(role)) ;
                 échec → formError = message générique

    noValidate sur le <form> désactive les bulles de validation du navigateur : on affiche nos propres messages (en français, sous chaque champ, reliés par aria-describedby).

    ProtectedRoute : 4 décisions dans l'ordre

    1. pas d'utilisateur → <Navigate to="/connexion" replace /> ;
    2. user.mustChangePassword → vers /mot-de-passe (aucune autre page tant que ce n'est pas fait, F04/RG04) ;
    3. roles fourni et le rôle de l'utilisateur n'y est pas → vers homePathFor(son rôle) ;
    4. sinon → affiche la page.
    Limite à retenir Cette protection est du confort d'affichage. Un utilisateur peut modifier le JavaScript de son navigateur. Seul le serveur protégera vraiment (vérifier le rôle sur chaque route API, NF02). Le code le rappelle en commentaire.

    Changement de mot de passe

    usePasswordForm(onDone) : champs current, next, confirm. Validation : actuel non vide ; passwordError(next) ; confirm === next. Puis changePassword(current, next) du contexte → authService.changePassword :

    • mot de passe actuel faux → AccountError('CURRENT') (on redemande l'ancien pour qu'une personne devant un poste ouvert ne puisse pas le changer) ;
    • règle non respectée → RULES ; identique à l'ancien → SAME ;
    • succès : user.password = new, mustChangePassword = false, renvoie l'utilisateur public. Le contexte fait setUser(...) : ProtectedRoute laisse alors passer.

    L'interface choisit quel champ afficher en erreur grâce au code de l'erreur (error.code === 'CURRENT' → sous « mot de passe actuel »), pas en lisant le texte.

    7. Accueil et chargement — features/home/, features/loader/

    Partie surtout visuelle. Ce qu'il faut savoir expliquer :

    HomePage.jsx

    • Affiche PageLoader (écran de chargement), la bande vidéo et le « hero » (bandeau avec texte, fond, particules, gélules, molécule).
    • useReadyWithTimeout(maxWaitMs=4000, minWaitMs) renvoie [isReady, markReady]. La page est « prête » quand (a) la molécule 3D a appelé markReady et (b) la durée minimale est écoulée (2,8 s à la première visite, 0 ensuite). Un minuteur de sécurité (4 s) appelle markReady de toute façon : la page ne reste jamais bloquée si la 3D échoue.
    • hasShownLoader est une variable hors du composant (module) : elle se souvient, pendant la session, que le loader a déjà été montré.
    • isRevealed ajoute la classe is-revealed au bandeau ; le composant Reveal (components/ui) déclenche alors ses animations d'apparition décalées (delay → variable CSS --reveal-delay).

    Les couches du bandeau (HomeHero.jsx, de l'arrière vers l'avant)

    1. background/ : paysage animé (HeroBackground, WaterRipple, useMouseParallax pour le léger déplacement avec la souris) ;
    2. particles/ : particules de lumière ;
    3. pills/ : les gélules ;
    4. HeroContent : le texte et la molécule 3D (molecule/, avec three, chargée à la demande par loadGlassMolecule.js et préchargée dès la page de connexion pour que l'accueil soit prêt plus vite).

    Les gélules (pills/)

    • usePillPile : toutes les 150 ms, une gélule est ajoutée et tombe ; elle se pose sur un tas. Le tas est une « carte des hauteurs » : un tableau avec une hauteur par colonne de 8 px. Pour chaque gélule, on essaie 6 positions et on garde la plus basse → un tas régulier. Maximum ≈ 3 couches sur la largeur (largeur × 3/50 gélules) et le tas s'arrête à 30 % de la hauteur.
    • Le tas est gardé dans une variable hors du composant (savedPile) : en quittant l'accueil puis en revenant, les gélules sont replacées directement, sans retomber. Si la fenêtre change de taille, on recommence après 300 ms de calme.
    • usePillHover : les gélules « sautent » quand la souris passe près. Chaque gélule a deux éléments (emplacement + gélule) pour que le saut aille toujours vers le haut de l'écran quel que soit l'angle.
    • Les gélules ont aria-hidden="true" : purement décoratives.
    Modification faite le 11/11 Avant, le code désactivait les gélules si le système demandait « réduire les animations » (prefers-reduced-motion). Sur ton PC (animations coupées dans Windows) elles avaient disparu. J'ai retiré ce test dans usePillPile.js et usePillHover.js et exclu .falling-pills de la règle globale de global.css qui coupe toutes les animations. Conséquence accessibilité : les personnes sensibles aux animations voient les gélules ; à signaler si un jury pose la question.

    Écran de chargement (features/loader/)

    PageLoader : fond uni + DotMolecule (petits points qui s'assemblent en molécule, positions dans moleculeDots.js). isVisible=false → fondu puis invisible et non cliquable. showImmediately : sans lui, il attend 200 ms avant de s'afficher (évite le clignotement d'un chargement très court). Un paragraphe role="status" invisible à l'écran annonce « Chargement de la page » aux lecteurs d'écran.

    8. Catalogue — features/catalogue/

    Exigences : F08 (par catégories), F09 (fiche produit), F10 (recherche), F11 (filtres), F12 (produits actifs et validés uniquement), RG07 (TTC = HT + TVA).

    8.1 Les données

    FichierRôle
    mockCatalogue.jscategories (3), laboratories (3 — ce sont les « fournisseurs »), products : 40 produits construits depuis un tableau de lignes [dossier, nom, format, description, catégorie, labo, prixHT, TVA, stock] avec rows.map(...).     8.2 catalogueStore.js

    • Un état unique { products, categories, stockMovements }. Au premier accès (load()) : il lit localStorage['gsb.catalogue'] ; si la forme est valide (isValidState : trois tableaux, produits avec id entier et name texte) il le garde, sinon il repart des mocks (structuredClone = copie profonde, pour ne jamais modifier les mocks d'origine).
    • updateCatalogue(change) : appelle change(état) qui modifie l'état directement, puis écrit dans le localStorage (try/catch : si c'est plein — une grosse image — la modif reste en mémoire), puis prévient les « écouteurs ».
    • onCatalogueChange(listener) : productService s'y abonne pour vider sa mémoire (cataloguePromise = null). Sans ça, après une modification admin, le catalogue du professionnel afficherait l'ancienne version.
    • readCatalogue() renvoie l'état ; nextId(items) = plus grand id + 1.

    8.3 productService.getCatalogue()

    • isSellable(product) : product.active && product.validationStatus === 'Accepté' (F12, RG08).
    • loadCatalogue() garde aussi seulement les produits dont la catégorie est active (désactiver une catégorie la retire du catalogue, F22). Renvoie { products, categories (actives), laboratories }.
    • Mémoire (cache) : la même promesse est réutilisée par le menu du catalogue et la page catalogue (un seul chargement). En cas d'échec on oublie le cache pour pouvoir réessayer.

    8.4 Recherche, filtres, tri — useCatalogueFilters(products, laboratories)

    • État filters : search, categoryId, laboratoryId, inStockOnly, sort (valeurs initiales dans INITIAL_FILTERS).
    • setFilter(name, value) change un critère sans toucher aux autres ({...previous, [name]: value}) ; useCallback pour une identité stable.
    • normalize(text) : normalize('NFD') sépare les lettres de leurs accents, la regex \p{Diacritic} les supprime, puis minuscules → « Éphélide » trouve « ephelide ».
    • visibleProducts (useMemo) : sépare la recherche en mots ; garde un produit si catégorie ok, labo ok, (en stock si demandé) et tous les mots sont dans « nom + nom du laboratoire ». Puis trie une copie ([...filtered], sinon sort() modifierait la liste d'origine) : prix croissant/décroissant sur priceHt, nom avec localeCompare(…, 'fr'), ou « pertinence » (ordre d'origine).
    • hasActiveFilters : sert à afficher « Tout effacer ».

    8.5 CataloguePage.jsx : l'assemblage

    • Charge les données avec useCatalogue ; utilise des tableaux vides créés une fois (NO_ITEMS) : un nouveau [] à chaque rendu relancerait le useMemo pour rien (React compare les références).
    • Filtres dans l'adresse : le menu envoie vers /catalogue?categorie=2 ou ?stock=1. useSearchParams les lit dans un useEffect. On ne fait pas confiance à l'adresse : Number(...) puis Number.isInteger && > 0, sinon la valeur est ignorée.
    • Construit des Map (id → laboratoire / catégorie) avec useMemo pour retrouver un nom en O(1) sur chaque carte.
    • Assemble : CatalogueBanner (vidéo), CatalogueFilters (labo, en stock, effacer), CatalogueToolbar (compteur, recherche, tri), CategoryChips, ProductGrid (cartes ProductCard, squelettes ProductCardSkeleton pendant le chargement).

    8.6 Cartes et fiche produit

    • ProductCard : image (ProductImage), nom, labo, prix TTC, StockBadge. useTilt incline la carte vers la souris (perspective(800px) rotateX/rotateY, ±6°) ; désactivé sur écran tactile (hover: hover) et si « réduire les animations ».
    • ProductImage : si product.image existe → <img loading="lazy" decoding="async"> (téléchargée seulement quand elle approche de l'écran) ; sinon une image provisoire (gélule + initiales des 2 premiers mots, aria-hidden).
    • StockBadge : 0 → « Rupture de stock » ; ≤ 10 → « Plus que N en stock » ; sinon « En stock ». Le texte porte l'information (pas seulement la couleur).

    cartService.js

    • MAX_QUANTITY = 99. Clé gsb.cart.<userId> : un panier par utilisateur (deux personnes sur le même PC ne partagent pas).

    utils/price.js : les calculs d'argent (RG07, RG20)

    FonctionCalcul
    priceWithTax(ht, tva)Math.round(ht × (1 + tva/100) × 100) / 100 → TTC arrondi au centime
    formatPriceIntl.NumberFormat('fr-FR', currency EUR) → « 12,50 € »
    formatVatRate2.1 → « 2,1 % »
    lineAmounts(ht, tva, qté)ht = ht×qté ; ttc = priceWithTax(ht, tva) × qté (prix unitaire TTC déjà arrondi × quantité → le total affiché = prix unitaire affiché × quantité) ; vat = ttc − ht, tout arrondi au centime
    cartTotals(lignes)additionne HT et TTC, TVA par taux (Map), arrondit à chaque addition : HT + TVA = TTC toujours exact
    Pourquoi arrondir à chaque étape ? En JavaScript, 0,1 + 0,2 = 0,30000000000000004 (virgule flottante). Arrondir au centime à chaque addition évite d'afficher ou de stocker ces erreurs. Ces calculs servent à l'affichage : le serveur refera les siens (on ne fait jamais confiance à un prix calculé dans le navigateur).

    10.1 orderService.createOrder(userId, { items, address, simulateFailure })

    1. await delay().
    2. Adresse : trim(), longueur 10 à 255 (même limite que la colonne SQL) sinon OrderError('ADDRESS').
    3. Panier : tableau non vide sinon EMPTY.
    4. Relit le catalogue (getCatalogue). Pour chaque ligne : produit introuvable, quantité non entière, < 1 ou > 99 → EMPTY ; quantité > stock → ajouté à stockIssues. Chaque ligne est construite avec nom, format, prix HT, TVA, prix TTC copiés du catalogue : les prix sont figés à la date d'achat (F19). Modifier un produit plus tard ne change pas les anciennes commandes.
    5. Si stockIssues non vide → OrderError('STOCK', …, details).
    6. Paiement simulé : si simulateFailure → OrderError('PAYMENT') et aucune commande n'est créée. Aucune donnée de carte n'est jamais demandée (RG18).
    7. changeStock(lines, -1) : le stock baisse une seule fois, ici (RG17).
    8. Crée l'objet commande : id (max des id de cet utilisateur + 1), reference, date (ISO), userId, status: 'En attente', deliveryAddress, lines, totals: cartTotals(lines), puis l'enregistre.

    Référence : GSB-AAAAMMJJ-XXXXXX. 6 caractères tirés avec crypto.getRandomValues (meilleur aléatoire que Math.random) dans un alphabet de 31 caractères sans ceux qu'on confond (pas de O/0, I/1, L). Une boucle do…while recommence si la référence existe déjà.

    OrderError(code, message, details) : l'interface réagit au code. isValidOrder filtre les données du stockage (forme vérifiée) comme pour le panier.

    17. Sécurité et RGPD

    Ce que le front fait bien

    • Pas de dangerouslySetInnerHTML ; tout texte utilisateur (adresse, motif de refus, nom de produit) est affiché comme texte.
    • Aucun secret côté front ; aucun mot de passe ni jeton dans le stockage navigateur ; toPublicUser retire le mot de passe.
    • Messages d'erreur génériques à la connexion (NF04) ; même réponse « introuvable » pour une ressource inexistante ou d'un autre (commande, produit).
    • Données du stockage re-validées à chaque lecture (sanitize, isValidOrder, isValidState).
    • Adresse d'URL non crue (?categorie= validé) ; image acceptée seulement si /produits/… ou data:image/….
    • Anti double envoi (isSubmitting), listes blanches de champs (cleanFields, updateProfile).
    • Police hébergée localement ; aucun script tiers.
    Ce que le front ne peut PAS garantir (à dire au jury)
    • Tout contrôle front (rôle, propriétaire d'une commande, produits d'un fournisseur, stock, prix) se contourne depuis la console du navigateur. Le serveur devra refaire chaque contrôle : droits sur chaque route (NF02), prix recalculés, stock transactionnel (RG17), validation des entrées (NF03).
    • Les mots de passe en clair dans mockUsers.js n'existent que pour la maquette ; le serveur stockera des hash bcrypt (NF01).
    • Le contrôle d'image (type, taille) doit être refait côté serveur (analyse du vrai contenu).
    • npm audit : 0 vulnérabilité au dernier passage.

    19. Questions probables d'un jury (avec réponses courtes)

    1. Pourquoi React et pas du HTML/JS simple ? Imposé par le sujet ; en plus, les composants réutilisables (bouton, tableau, formulaire) et l'état partagé (utilisateur, panier) évitent de dupliquer.
    2. Pourquoi des hooks séparés des composants ? Le composant affiche, le hook gère la logique : plus lisible, testable, et réutilisable (ex. PasswordForm sert à la première connexion et dans « Mon compte »).
    3. Comment le panier évite-t-il les prix falsifiés ? Il ne stocke que produit + quantité ; les prix sont relus dans le catalogue ; la commande fige les prix, et le serveur les recalculera.
    4. Un utilisateur peut-il voir la commande d'un autre ? Le service ne lit que les commandes de l'utilisateur connecté et répond « introuvable » sinon. Mais c'est le serveur qui devra l'imposer, car le front se contourne.
    5. Pourquoi le même message d'erreur à la connexion ? Pour ne pas révéler quelles adresses ont un compte (NF04).
    6. Comment gérez-vous le stock ? Décrémenté une seule fois à la création, remis si annulation, annulation définitive ; ajustements admin avec motif et historique. Le serveur utilisera une transaction (RG17).
    7. Pourquoi useCallback / useMemo ? Garder la même fonction/valeur entre deux rendus pour ne pas relancer un effet ou un calcul inutilement (ex. useLoader(load)).
    8. Où sont les risques XSS ? Aucun dangerouslySetInnerHTML ; React échappe le texte ; les images sont limitées à /produits/ ou data:image/.
    9. Que se passe-t-il si le stockage navigateur est bloqué ? Chaque accès est dans un try/catch : l'appli marche, sans mémoire entre deux pages.
    10. Qu'est-ce qui reste à faire ? Le back-end (API, MySQL, auth serveur), les tests multi-navigateurs, Lighthouse, mentions légales / cookies, et refaire les images produits (marques réelles).
